# 版本、提交与推送规范

本文维护版本与源码交付规则。当前实现和人工待验见 [STATE](STATE.md)，任务与验收流程见 [WORKFLOW](WORKFLOW.md)。制定规范不代表授权提交、推送、打标签或发布。

本地打包仅供自用与本地验证，不用于发布。发布包统一由 GitHub Actions 原生构建 Apple Silicon / Intel 两个架构，通过检查后上传 GitHub Release；不得用本地包替换或补齐云端发布资产。

## 1. 版本定位

首个可分享版本建议为 `0.1.0-alpha.1`，定位为个人学习版的功能预览。此为下一次发版目标，当前文件中的 `0.0.1` 在实际准备该版本时再统一修改。

版本反映已交付能力与稳定性承诺，不按任务卡数量或 M0 / M1 / M2 编号递增。阶段出口按下表判断，不预设发布日期。

| 版本阶段 | 出口条件 |
|---|---|
| `0.1.0-alpha.N` | 核心链路可构建、可验证，公开已知限制与人工待验项；只面向知情测试者 |
| `0.1.0-beta.N` | 冻结本版范围，范围内原生人工验收完成，进入真实使用与兼容性验证 |
| `0.1.0-rc.N` | 本版功能和文档齐备，无已知阻断问题，最终包通过安装、升级与核心场景验证 |
| `0.1.0` | 同一候选的发布门槛全部通过，交付首个明确范围的个人学习版 |
| `0.2.0` 及后续次版本 | 增加完整、可验收的用户能力；T-018 / T-019 可作为候选范围，实施仍须任务卡批准 |
| `1.0.0` | 核心行为与兼容合同稳定，面向普通用户的分发、新机安装及升级路径通过验收 |

M3 的智能分类、Vision 等增强能力不自动成为 `1.0.0` 的前置条件。正式分发的签名、公证、系统支持范围和更新方式须先明确范围与任务；当前个人学习版仍遵循 [ADR-006](decisions/ADR-006-self-contained-app.md)。

## 2. 递增规则

采用 `主版本.次版本.修订版本[-预发布阶段.序号]`，标签统一加 `v`，如 `v0.1.0-alpha.1`。配置文件中的版本不带 `v`。

| 变更 | 规则与示例 |
|---|---|
| 同一预发布目标的修复、补验 | 递增序号，如 `0.1.0-alpha.1` → `0.1.0-alpha.2` |
| 进入下一预发布阶段 | 从序号 1 开始，如 `0.1.0-alpha.3` → `0.1.0-beta.1` |
| 兼容性修复 | 递增修订版本，如 `0.1.0` → `0.1.1` |
| 新增用户能力 | 递增次版本、修订归零，如 `0.1.2` → `0.2.0`；需要试用时加预发布后缀 |
| `0.x` 阶段的破坏性变更 | 递增次版本，并显式说明迁移与回退边界 |
| `1.0` 起的破坏性变更 | 递增主版本、其余归零，如 `1.3.2` → `2.0.0` |
| 纯文档、测试或内部整理 | 通常不单独发版，随下一次用户可见发布交付 |

发布过的版本、标签和资产不可覆盖。已分发的包需要改变内容时使用新版本；只在本地、尚未分发的候选可以重建。修复 RC 后递增 RC 序号并重新完成受影响验收；RC 转无后缀版本也须核对最终重建包。

版本只在准备发布时变更，普通提交不逐次改版本。任何会影响既有 CLI 参数、JSON 输出、配置 / 预设 Schema、数据目录或输出策略的修改，都要说明兼容性；`0.x` 不免除保护原图和已有用户数据的责任。

## 3. 版本来源与追溯

产品共用一个版本，以根 `Cargo.toml` 的 `[workspace.package].version` 为准；三个 Rust package 继续使用 `version.workspace = true`。发版时同步：

- `src-tauri/tauri.conf.json` 的 `version`。
- `ui/package.json` 的 `version`，即使它是不发布的私有包。
- `Cargo.lock` 中 `yali-core`、`yali-cli`、`yali-app` 的版本，由 Cargo 正常刷新；不顺带升级外部依赖。
- 本次发布说明、标签及资产文件名中的版本。

由 GitHub Actions 从目标提交重建最终 App，核对包内 CLI 的 `--version` 与产品版本一致，检查生成的 `Info.plist` 版本字段符合平台格式及发布顺序，尤其是预发布后缀的处理；不要直接修改已签名包。实际最低系统与架构以包内引擎和最终产物为准。

每次发布记录版本、完整提交 SHA、构建环境、实际系统 / 架构要求、验证结果、已知问题及资产 SHA-256。包内 CLI、GUI 与资源来自同一候选源码。版本号不能替代提交 SHA；普通开发构建也应在交付说明中记录 SHA 和未提交修改。

## 4. 提交规范

使用 `type(scope): 中文结果说明（T-xxx）`，跨模块修改可省略 scope。类型限定为 `feat`、`fix`、`refactor`、`perf`、`test`、`docs`、`build`、`ci`、`chore`、`revert`。scope 选实际模块，如 `core`、`cli`、`app`、`ui`、`workflow`、`release`；只采用与改动相关的类型和范围。

```text
fix(app): 修复预览缓存授权遗漏（T-024）
feat(core): 持久化失败件队列（T-018）
docs(release): 制定版本与源码交付规范（T-027）
chore(release): 准备 0.1.0-alpha.1（T-xxx）
```

一个提交只解决一个可描述、可回退的问题；一张卡允许多个连贯提交，一个 PR 对应一张卡。避免把无关修复、样式调整和依赖更新装在同一提交。发布准备使用独立卡，汇总纳入版本的功能卡。历史提交不因新规范而改写；后续使用 `fix`，不再使用 `fixed`。

提交前查看完整暂存差异，按明确路径暂存，保留其他工作区修改。按 [AGENTS](../AGENTS.md) 运行范围内检查，卡片附实际命令、退出结果与人工待验。CLI 改动还须运行相关 CLI 测试。纯文档检查差异、链接与事实一致性即可。

非显然的修改在正文写明原因、验证与兼容性。涉及数据迁移、删除、安装器或分发时补充回退方式；破坏性变更在标题加 `!`，正文使用 `BREAKING CHANGE:` 说明影响与迁移。人工未验必须写明，不能因自动测试通过而标完成。

## 5. 分支与合入

沿用现有 `dev` / `main`，不增加常驻 release 分支：

- `dev` 承载当前开发与集成；允许存在已记录的人工待验项。
- `main` 保存经过审查、可构建、可追溯的交付基线；预发布版本须明确标注阶段，合入不自动代表正式发布。
- 任务分支按需、经用户要求再创建，可使用 `feat/T-018-failed-queue`、`fix/T-024-preview`、`docs/T-027-versioning`。
- 任务 PR 默认合入 `dev`；发布整合 PR 从 `dev` 合入 `main`，绑定独立发布卡，列出纳入的功能卡，不混入新的功能实现。单人本地直接合入也须用户明确授权、满足同样检查并记录来源和目标 SHA。

不开工自动建分支，不自动 pull，不为套用规则改写历史。已有同卡提交可保留，不要求重写；若需要 squash 或 rebase，先说明影响并获得用户明确授权。已推送到共享分支的历史保持不变，修复使用新提交。

## 6. 推送规范

提交、推送、合入、打标签、发布分别按用户明确授权执行；用户一次授权整条链路时可连续完成，不重复确认。仅要求“提交”不包含推送，“推送当前分支”不包含推送标签或发布资产。

推送前核对当前分支、完整 HEAD、远端地址、认证身份、待推提交范围及目标远端分支。远端状态在获准操作时重新读取；本地 `origin/*` 仅是上次同步记录。`dev` 没有上游时，先明确是否推送为 `origin/dev`，不能默认改推 `main`。

仅推送明确指定的分支和提交；需要标签时单独核对并推送指定标签。禁止默认使用 `--all`、`--mirror`、`--tags` 或强推。远端领先或出现分叉时停止推送，说明差异并确认整合方式，不自动 reset、rebase 或覆盖远端。

推送后读回远端分支 / 标签 SHA 并与本地核对。有适用 CI 时跟踪到最终状态；没有 CI 时明确报告未配置，不能把上传成功当作检查通过。网络超时先查远端实际状态，再决定是否重试。

## 7. 发布门槛

发版前明确预发布或稳定渠道，并逐项记录：

1. 发布范围、基线与候选 SHA 固定，目标版本及兼容性说明完整；候选不混入无关或未追踪修改。
2. Rust 三个 package 测试通过，UI 测试与构建通过；完整 App 使用 `bash scripts/build.sh` 重建，确认真实前端、包内依赖、签名和 UTI 检查通过。
3. 最终 App 的隔离运行与安装场景通过；压缩质量相关变更按 [benchkit](../benchkit/README.md) 使用重建后的 CLI 验证，不复用旧二进制。
4. 依据本版范围检查 Finder、通知、GUI、剪贴板、watch 和配置升级。Alpha 可保留明确披露的人工待验；Beta 及后续阶段满足上表出口。已知数据丢失或原图破坏问题阻断所有渠道。
5. 发布说明列用户可见变化、最低系统 / 架构、首次运行限制、已知问题与人工待验；当前 ad-hoc 包不得宣称 Developer ID 签名或公证通过。
6. 在获准合入后，由 GitHub Actions 从 `main` 的最终目标提交分别构建并核对两个架构；获准打标签时创建附注标签，绑定该提交，发布资产记录云端运行来源与 SHA-256。本地验证结果不能替代云端运行通过。
7. 获准推送 / 发布后，读回远端标签、Release 渠道、实际资产及校验和；预发布标记与版本后缀一致。

macOS 双架构自动构建与 Release 草稿由 [T-028](tasks/T-028-macos-release.md) 实施，运行方式与验证边界见 [RELEASING](RELEASING.md)。手动运行只生成测试产物，推送合法标签才自动创建草稿；公开发布仍需单独授权。不自动递增版本、提交或推送，未引入提交钩子。
