# 版本与源码交付

Yali 使用 SemVer 形式的版本号，并允许 `alpha`、`beta`、`rc` 预发布后缀。当前源码版本为 `0.3.0-alpha`，表示功能预览，不代表所有系统入口都完成了人工验收。

## 版本规则

- 修复兼容性问题递增 patch，例如 `0.1.0` 到 `0.1.1`。
- 增加用户能力递增 minor，例如 `0.1.0` 到 `0.2.0`。
- `0.x` 阶段的破坏性变化也递增 minor，并在发布说明写清迁移和回退边界。
- `1.0` 以后，破坏性变化递增 major。
- 纯文档、测试和内部整理通常随下一次用户可见版本交付，不单独发版。
- 预发布阶段按 `0.1.0-alpha`、`0.1.0-beta`、`0.1.0-rc` 推进，阶段切换需要重新检查受影响功能。

版本号只在准备发布时变更。普通开发提交不逐次修改版本，也不把版本号当作提交 SHA 的替代品。

## 版本来源

根 `Cargo.toml` 的 `[workspace.package].version` 是产品版本来源。发布准备时同步：

- `src-tauri/tauri.conf.json` 的 `version`。
- `ui/package.json` 的 `version`。
- `Cargo.lock` 中工作区包的版本记录。
- 标签、Release 标题、资产文件名和变更记录。

发布前运行：

```bash
python3 scripts/release.py check
```

由 GitHub Actions 从固定提交重建 App，核对包内 CLI、Info.plist、架构和实际最低系统。不要直接修改已经签名的包来伪造版本或系统要求。

## 提交与分支

提交信息使用 `type(scope): 中文结果说明`，类型限定为 `feat`、`fix`、`refactor`、`perf`、`test`、`docs`、`build`、`ci`、`chore`、`revert`。一个提交只解决一个可描述的问题。

`dev` 用于日常开发和集成，`main` 只保存可发布基线。任务分支按需创建，默认合入 `dev`。发布整合从 `dev` 进入 `main`，发布标签只指向已合入 `main` 的提交。

提交、推送、合入、标签和发布分别需要明确授权。远端领先、分叉或存在未知标签时先停止，读取远端实际状态后再决定整合方式。强制推送或历史改写必须单独说明影响和回退办法，并取得明确的“是 / 确认 / 继续”。

## 发布追溯

每次发布记录：版本、完整提交 SHA、构建环境、架构、实际最低系统、验证结果、已知问题、人工待验和资产 SHA-256。发布包、CLI 和资源必须来自同一候选提交，不能把本地旧产物混入云端 Release。
