# 开发工作流

项目把“开发过程”和“公开文档”分开：过程记录放在 `.tasks/`，用户可读的长期资料放在 `docs/`，已完成的用户可见变化进入 `docs/CHANGELOG.md`。

## 从想法到交付

### 1. 先确认范围

先说明问题、用户场景、影响范围和不做的部分。涉及 UI、数据迁移、系统 Services、发布或平台支持时，先查对应设计文档和架构决策。

### 2. 创建任务卡

在 `.tasks/` 新建 `NNN-short-name.md`，写清：

- 背景与目标
- 范围、非目标和兼容性影响
- 验收条件，包括自动化和人工验收
- 计划运行的命令
- 风险、回退和需要用户确认的动作

任务卡不进入 `docs/`，也不作为 README 的长期链接。任务编号可以连续使用，但不要求与版本号绑定。

### 3. 实现与验证

先读后写，优先复用现有内核和数据边界。每次改动保持可回退，完成后运行与范围匹配的测试。自动化通过只说明代码或脚本达到条件，Finder、通知、托盘、剪贴板、watch、窗口手感和真实兼容性仍需人工验收。

### 4. 记录交付

任务卡记录实际命令、结果、构建来源、人工待验和回退方式。用户可见变化整理到 CHANGELOG，当前事实更新到 STATE。只有稳定规则、架构约束和可重复的操作说明才进入其他 `docs/` 文件。

### 5. 关闭任务

任务没有未完成的必要工作后，把状态标为完成；若有人工验收未做，保留“待人工验收”，不能写成完成。任务卡仍可留在本地 `.tasks/` 供开发追溯，但不会成为公开文档的一部分。

## 任务卡模板

```markdown
# NNN · 简短标题

状态：进行中

## 目标

## 范围与非目标

## 验收条件

- [ ] 自动化：
- [ ] 人工：

## 验证记录

命令、日期、结果和环境。

## 风险与回退
```

## 文档更新原则

README 面向首次访问项目的人，写动机、能力、安装和限制。`docs/` 面向用户和贡献者，写稳定规则。`.tasks/` 面向当前开发者，写过程和证据。三者不重复粘贴同一段历史，也不把未验证的计划写成已实现能力。
